| D20 | 28/10/2026 | SentinelSSH devient un site multi-comptes : inscription libre (nom + mot de passe de 12 caractères minimum, sans e-mail ni confirmation), chaque compte ne voit que ses analyses et ses récidivistes. Table `roles` (`admin`, `user`) ; `users.role_id` (chaque compte a un seul rôle) ; `analyses.user_id` avec `ON DELETE CASCADE`. L'administrateur gère les comptes (liste, suppression des comptes `user`) mais ne voit pas leurs analyses ; un compte admin ne peut pas être supprimé par l'API ; il n'est créé que par `flask create-admin`. Un `user` peut supprimer son compte (mot de passe redemandé). Noms uniques sans tenir compte des majuscules (`COLLATE NOCASE`), mot de passe de 12 à 128 caractères. Tentatives limitées par IP (5 échecs de connexion en 15 min, 5 inscriptions par heure, en mémoire). Remplace D7 et D15 ; la mise en ligne (serveur, HTTPS) reste à venir | Garder un administrateur unique (D7) ; admin qui voit toutes les analyses ; inscription avec e-mail et confirmation ; rôle stocké en texte dans `users` | L'objectif du projet est un site où chacun dépose son journal et profite des analyses. La sécurité repose sur un filtre `WHERE user_id = ?` dans chaque requête (une analyse d'un autre compte répond 404, comme un id inconnu). Pas d'e-mail : une donnée personnelle de moins à protéger (minimisation RGPD). Une table `roles` garantit par une clé étrangère qu'un compte a toujours un rôle valide. L'admin qui ne voit pas les analyses applique la minimisation : gérer un compte ne demande pas de lire ses données. Le compte est relu à chaque requête : un compte supprimé perd l'accès tout de suite. Ajouts après la revue de code : sans limite haute, un mot de passe de 40 Mo serait haché (déni de service) ; `Admin` pourrait imiter `admin` ; un admin pourrait effacer un autre admin et ses analyses ; un outil anti-force-brute doit se protéger lui-même de la force brute (compteurs en mémoire : simples, sans dépendance, suffisants avant la mise en ligne) |
| D21 | 28/10/2026 | Profils de compte. Onglet « Mon compte » (`/compte`) pour le user ; pour l'admin, onglet « Comptes » (`/comptes`) où son compte est séparé en haut, puis la liste ; profil d'un user vu par l'admin à `/comptes/<id>`. Chacun modifie son nom et son mot de passe (`PATCH /api/auth/me`, ancien mot de passe redemandé) ; seul un user supprime son compte. L'admin change le nom, réinitialise le mot de passe et supprime le compte d'un user (`PATCH`/`DELETE /api/users/<id>`) et peut supprimer une de ses analyses sans la lire (`DELETE /api/users/<id>/analyses/<id>`) ; il n'en voit que la date et le nom du fichier, jamais le mot de passe. Un compte admin ne se gère jamais par `/api/users` (403). Ids des comptes et des analyses en UUID (uuid4) ; colonne `users.updated_at` | Suppression du compte sur la page d'analyse ; admin qui lit les analyses ; ids entiers ; `updated_at` sur toutes les tables ; 4 routes séparées pour le nom et le mot de passe | Une page « compte » rassemble ce qui concerne le compte (au lieu d'un bloc perdu sous l'analyse). L'admin doit pouvoir aider (renommer, réinitialiser, supprimer à la demande) sans accéder aux données : minimisation RGPD. Redemander l'ancien mot de passe empêche de voler un compte depuis une session ouverte ; ses échecs comptent dans la limite de connexion. Un UUID ne se devine pas et ne révèle pas le nombre de comptes ou d'analyses (en plus du filtre `user_id`) ; il supprime aussi le cas `SQLITE_MAX_INT`. `updated_at` seulement sur `users` : une analyse n'est jamais modifiée. `PATCH` = modifier une partie d'une ressource : une route au lieu de quatre |
| D22 | 28/10/2026 | Sécurité avant la mise en ligne. **Session** : on garde la session signée de Flask (pas de JWT) ; sa durée de vie est lue dans `.env` (`SESSION_LIFETIME_MINUTES`, 60 min sans requête) ; elle est refusée si le nom ou le mot de passe a changé depuis son ouverture (`logged_at` comparé à `users.updated_at`, dates à la milliseconde). **CORS** : flask-cors sur `/api/*`, seulement les origines de `CORS_ORIGINS` (`.env`), cookie compris. **Base chiffrée** : SQLCipher (`sqlcipher3`), clé de 64 caractères hexadécimaux dans un fichier hors du dépôt (`DB_KEY_FILE`), que seul l'administrateur du serveur détient ; sans clé ou avec une mauvaise, le site refuse de démarrer. Exception à la règle « SQL paramétré » : `PRAGMA key` n'accepte pas `?`, la clé est donc écrite dans la commande, mais seulement après avoir vérifié qu'elle fait exactement 64 caractères 0-9 a-f | JWT dans un cookie HttpOnly ; JWT dans l'en-tête `Authorization` (localStorage) ; pas de CORS ; clé de la base écrite dans `.env` ; chiffrer seulement certaines colonnes | La session Flask est déjà un jeton signé (HMAC, itsdangerous) dans un cookie HttpOnly : un JWT y mettrait le même contenu avec la même signature ; son seul atout, un format lisible par d'autres programmes, ne sert pas ici. Le vrai manque était la durée de vie et la révocation : une session ouverte restait valide après une réinitialisation du mot de passe par l'admin. Le front et l'API ont la même origine (proxy Vite, puis Flask sert le front) : CORS ne sert qu'à autoriser explicitement un front ailleurs ; sans en-tête, le navigateur bloque tout le reste. Le chiffrement protège la base copiée seule (sauvegarde, disque, dépôt par erreur) : noms, dates et IP (données personnelles, RGPD) deviennent illisibles ; les mots de passe étaient déjà hachés. La clé hors du dépôt et hors de `.env` ne part jamais avec le code. Limite : sur le serveur en marche, la clé est en mémoire, le chiffrement ne protège pas d'une prise de contrôle du serveur |
| D23 | 29/10/2026 | Audit complet. **Lecture du journal** : le nom d'utilisateur est libre ; l'IP est le dernier « from <IP> port <n> » de la ligne et doit être une vraie IP (module `ipaddress`). **Envoi** : un fichier vide, ou sans aucune tentative de connexion SSH, est refusé (400, rien d'enregistré) ; UTF-16 et BOM lus. **API** : un corps JSON qui n'est pas un objet répond 400. **Stockage** : comptes visés en JSON. **Compte** : renommer son compte redemande aussi le mot de passe actuel ; `create-admin` applique les règles de l'inscription | Garder `(\S+)` ; enregistrer une analyse vide avec le verdict « rien de suspect » ; refuser l'UTF-16 | L'attaquant choisit le nom d'utilisateur, que sshd écrit tel quel : avec le nom « x from 8.8.8.8 port 22 », l'ancien parser accusait 8.8.8.8 et proposait de la bloquer (usurpation, faille connue de fail2ban) ; un nom avec une espace rendait même l'attaque invisible. sshd écrit la vraie IP en dernier : `(.*)` gourmand la trouve. Un « rien de suspect » sur un mauvais fichier donnerait un faux sentiment de sécurité. PowerShell enregistre en UTF-16. Une virgule dans un nom le coupait en deux à l'affichage. Avec une session laissée ouverte, n'importe qui pouvait renommer le compte : son propriétaire ne connaissait plus son nom de connexion. Coût mesuré : 50 Mo lus en 4,6 s au lieu de 3,9 s |
